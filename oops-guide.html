How OOP is Used in Cardora

A comprehensive explanation of Object-Oriented Programming (OOP) concepts, class hierarchies, and design patterns implemented in the Cardora Greeting Card Studio.

1. The Four Core OOP Pillars

Cardora directly implements every fundamental OOP pillar within its graphics and state management engine:

A. Abstraction

Complex graphics routines, canvas coordinate transformations, and mathematical hit-testing are abstracted behind clean, intuitive method signatures. Users and view controllers interact only with high-level contracts like element.render(ctx) or card.addElement(el) without needing to manage low-level canvas matrices directly.

B. Encapsulation

Element and card properties (coordinates _x, _y, dimensions _width, _height, opacity _opacity, rotation _rotation) are kept strictly private using underscore prefixes. Access is controlled exclusively through validated getters and setters that enforce boundary safety.

// Encapsulation in src/models/CardElement.js export class CardElement { constructor({ x = 50, y = 50, width = 100, height = 100 } = {}) { this._x = Number(x); this._y = Number(y); this._width = Math.max(10, Number(width)); // Minimum width boundary enforced this._height = Math.max(10, Number(height));// Minimum height boundary enforced } // Safe public getters & setters get width() { return this._width; } set width(val) { this._width = Math.max(10, Number(val)); } }

C. Inheritance

The specialized card items (TextElement, ShapeElement, and SvgElement) inherit all shared spatial properties, bounding boxes, hit-testing, and coordinate math from the base abstract class CardElement.

CardElement (Base Abstract Class)
x, y, width, height, rotation, opacity, containsPoint()
↓ extends
TextElement
fontFamily, fontSize, color, textAlign, textShadow
ShapeElement
shapeType, fill, stroke, strokeWidth, dashArray
SvgElement
svgKey, src, cachedImage, preserveAspectRatio

D. Polymorphism

Polymorphism allows the renderer to process an array of heterogeneous card elements uniformly. When CardRenderer paints the card, it simply invokes element.render(ctx). At runtime, the JavaScript virtual machine dynamically dispatches the specific overridden implementation:

  • TextElement.render(ctx) renders multi-line typography with text-alignment and baseline metrics.
  • ShapeElement.render(ctx) renders geometric paths (rectangles, circles, hearts, stars, diamonds).
  • SvgElement.render(ctx) draws anti-aliased scalable vector illustrations from cached buffers.
// Polymorphic Rendering Loop in src/services/CardRenderer.js render(card, options = {}) { card.renderBackground(this._ctx); // Pure Polymorphism: Same method call, different element behaviors card.elements.forEach(element => { element.render(this._ctx, options); }); }

2. Composition Over Inheritance

While elements inherit from CardElement, the top-level GreetingCard class uses Composition ("has-a" relationship) rather than inheritance:

  • A GreetingCard has an array of CardElement objects.
  • It manages their z-order stacking (bringForward, sendBackward), element lifecycles (addElement, removeElement, duplicateElement), and canvas dimensions.
// Composition in src/models/GreetingCard.js export class GreetingCard { constructor({ title = 'Celebration', elements = [] } = {}) { this._title = title; this._elements = []; // Composed collection of CardElement instances elements.forEach(el => this.addElement(el)); } }

3. Design Patterns Implemented

Cardora leverages industry-standard software design patterns to maintain loose coupling and high cohesion:

1. Memento Pattern (Undo & Redo)

HistoryManager captures serialized snapshots of the GreetingCard state prior to any mutation. It maintains two stacks (_undoStack and _redoStack), allowing effortless rollbacks without leaking internal class references.

2. Factory Method Pattern (Template Catalog)

TemplateService encapsulates the instantiation of complex card templates. It produces ready-to-render GreetingCard instances configured with pre-composed typography and vector graphics.

3. Strategy Pattern (Decoupled Rendering)

The card model does not directly write to DOM canvas elements. Instead, rendering strategies are handled by external services:

  • CardRenderer: Interactive onscreen editing with selection outlines and bounding anchor handles.
  • ExportService: Offscreen supersampled rendering producing clean, print-quality PNG/JPEG files without UI controls.
  • AnimationController: 60 FPS physics loop applying entrance transforms and particle motion.

4. Viva & Evaluator Questions & Answers

Q1: What are the main classes in your project and their responsibilities?

Ans: GreetingCard is the composite entity managing the card's dimensions and layers. CardElement is the abstract base class for placed objects. TextElement, ShapeElement, and SvgElement represent concrete visual objects. CardRenderer, TemplateService, HistoryManager, and ExportService represent the service layer.

Q2: How does your code demonstrate Polymorphism?

Ans: In CardRenderer.render(), we iterate over a polymorphic list of CardElement objects and invoke element.render(ctx). Each subclass implements its own rendering logic without the renderer needing to check element types with conditional statements (no if (type === 'text')).

Q3: How would this architecture translate to Java (JavaFX or Swing)?

Ans: The architecture maps 1:1 to Java. CardElement becomes an abstract class CardElement implementing a Renderable interface. TextElement, ShapeElement, and SvgElement extend it. The CardRenderer receives a GraphicsContext (JavaFX) or Graphics2D (Swing) instead of the HTML5 canvas context.

Q4: Why did you choose Composition for the GreetingCard class?

Ans: Adhering to the "Composition over Inheritance" principle, a card is not a special type of element; rather, it aggregates and coordinates multiple elements. Composition provides greater flexibility to add, remove, and reorder elements dynamically at runtime.
